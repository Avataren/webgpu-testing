# Event System for Script Communication

The event system enables scripts to communicate with each other through a publish-subscribe pattern. Scripts can emit events that other scripts can subscribe to and handle.

## Features

- **Event Emission**: Scripts can emit named events with arbitrary data
- **Event Subscription**: Scripts can subscribe to events and specify callback functions
- **Event Unsubscription**: Scripts can unsubscribe from events they no longer want to receive
- **Automatic Cleanup**: Event subscriptions are automatically cleaned up when entities are destroyed
- **Command Buffering**: Events are queued during script execution and dispatched after all scripts update

## API Functions

### emit_event(event_name: String, data: Value)

Emit an event that can be received by subscribed scripts.

**Parameters:**
- `event_name`: The name of the event to emit
- `data`: The event data (can be any Rune value: string, number, object, array, etc.)

**Example:**
```rune
pub fn update(self_entity, dt) {
    if is_key_just_pressed("Space") {
        emit_event("player_jumped", #{
            entity: self_entity,
            height: 5.0,
            velocity: 10.0
        });
    }
}
```

### subscribe_event(event_name: String, callback_name: String)

Subscribe to an event with a callback function. The callback will be called when the event is emitted.

**Parameters:**
- `event_name`: The name of the event to subscribe to
- `callback_name`: The name of the function to call when the event is received

**Example:**
```rune
pub fn on_created(self_entity) {
    subscribe_event("player_jumped", "on_player_jumped");
}

pub fn on_player_jumped(event_data) {
    log_info(`Player jumped with height: ${event_data.height}`);
}
```

**Note:** The callback function must:
1. Be a public function in the same script
2. Accept exactly one parameter: the event data
3. Be defined before calling subscribe_event

### unsubscribe_event(event_name: String)

Unsubscribe from an event. The current entity will no longer receive notifications for this event.

**Parameters:**
- `event_name`: The name of the event to unsubscribe from

**Example:**
```rune
pub fn update(self_entity, dt) {
    if is_key_just_pressed("U") {
        unsubscribe_event("player_jumped");
        log_info("Unsubscribed from player_jumped");
    }
}
```

## Event Flow

1. **Script Execution**: All scripts run their `update()` functions
2. **Event Queueing**: Calls to `emit_event()` add events to a queue
3. **Command Application**: Script commands (entity spawning, component changes, etc.) are applied
4. **Event Dispatch**: Queued events are dispatched to subscribed entities
5. **Callback Execution**: Each subscriber's callback function is called with the event data
6. **Callback Commands**: Any commands generated by callbacks are applied

## Usage Patterns

### Simple Notification

```rune
// Emitter
if something_happened {
    emit_event("notification", "Something happened!");
}

// Listener
pub fn on_created(self_entity) {
    subscribe_event("notification", "handle_notification");
}

pub fn handle_notification(event_data) {
    log_info(event_data);
}
```

### Data Passing

```rune
// Emitter
emit_event("enemy_spawned", #{
    position: [x, y, z],
    health: 100,
    type: "zombie"
});

// Listener
pub fn on_enemy_spawned(event_data) {
    let pos = event_data.position;
    let health = event_data.health;
    // React to new enemy
}
```

### State Synchronization

```rune
// Game Manager
pub fn update(self_entity, dt) {
    if game_over {
        emit_event("game_state_changed", #{
            state: "game_over",
            score: final_score
        });
    }
}

// UI Script
pub fn on_game_state_changed(event_data) {
    if event_data.state == "game_over" {
        // Update UI to show game over screen
    }
}
```

3. Press the keys mentioned above and watch the console for event logs

## Best Practices

1. **Event Names**: Use clear, descriptive names like "player_jumped" instead of "event1"
2. **Event Data**: Use objects (maps) for event data to make it self-documenting
3. **Cleanup**: Unsubscribe from events when no longer needed to avoid unnecessary processing
4. **Error Handling**: Event handlers should be defensive and handle missing or invalid data
5. **Performance**: Be mindful of emitting events every frame; prefer state changes or significant events

## Architecture Notes

- Events are processed after all scripts have updated but before the next frame
- Event handlers run in the context of the subscribing entity
- Multiple scripts can subscribe to the same event
- Events are not persisted; they only exist for one frame
- Event subscriptions are stored per entity and automatically cleaned up when entities are destroyed
